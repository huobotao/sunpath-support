Candidate-version tool documentation — not an App Store release announcement. Production iCloud/CloudKit configuration, final signing and testing on real devices have not been accepted yet. This explanation covers the data handling implemented for the NetPulse candidate: device-interface estimates, optional photo-library counts and user-started cloud upload probes. It is not a declaration that App Store privacy answers or a release have been approved.

Network observations stay on the device

NetPulse reads device network-interface byte counters and link status to estimate upload/download rates, show a recent chart and calculate totals for the current process sampling session. It does not inspect packet content, browser history or individual apps' traffic. Rates may include other apps and system services; interface data may be incomplete or reset. Low or zero readings do not establish that the device or iCloud is idle.

These readings, the activity reference and optional photo counts are processed in memory on the device. This candidate has no developer account registration, advertising SDK, behavioural analytics or feature that sends these readings to a developer server. Cloud probes described below do upload data to Apple, so the app is not entirely offline and does not promise that no data is uploaded.

Optional photo-library statistics

Photo access is requested only when you choose the photo-statistics action. If access was previously granted, the app can refresh the counts. It queries the number of photo/video items visible within your permission scope and the number with a creation time in the last 24 hours. It does not request image/video bytes, thumbnails or media playback and does not edit or delete your library.

Hidden items are excluded and burst items follow the library's counting rules. Limited access covers only the items the system makes available, not your entire library. You can decline photo access and still view network sampling. Creation dates and counts cannot identify pending uploads, completed sync, the iCloud Photos queue, total bytes or remaining bytes. Permissions can be managed in the device's system settings.

An iCloud Drive test uploads a generated file

Only when you start the Drive probe, the app checks whether an iCloud identity is available, resolves its own iCloud Drive container and creates a randomly generated test file there. The default payload is 8 MiB (8,388,608 bytes). The probe observes that file's system-reported upload state and estimates its average throughput, including system scheduling delays. It does not enumerate your personal Drive documents or use them as test data.

Apple's iCloud service processes the generated file and associated service requests. An active probe consumes network data and storage and can be affected by metered connections, account limits and system scheduling. It does not report the progress, size, remaining data or speed of the system-wide iCloud queue.

A CloudKit test uses the app's private database

Only after you start a CloudKit probe, a configured build contacts Apple to check CloudKit account availability and obtains the account's CloudKit user-record identifier. The identifier is kept in memory for account-consistency checks before and after operations. It is not your password or verification code, and this candidate does not send it to a developer server.

The app creates a random local test file, by default 5 MiB (5,242,880 bytes), and saves it as an asset in a new record in this app's CloudKit private database for your account. The record includes its creation time, payload size, a random record name and a separate random per-probe ownership token. The token is used to verify that an exact record belongs to the current probe before deletion; it is not an advertising identifier or sign-in credential.

Apple processes the test asset, record fields, account checks and related service requests. The app divides the payload size by the duration of the save operation, which includes connection and metadata overhead. It is a single test result, not a measure of every iCloud upload. The CloudKit container, account association, Production schema and signed capabilities must be verified before release. Apple's handling of iCloud and CloudKit is explained in Apple's privacy information.

Cancellation, cleanup and possible residual data

The app attempts to remove the exact Drive test file it created and, for CloudKit, the exact matching test record and local temporary file. Cleanup failures remain visible and provide a retry within the same running process. A pending cleanup prevents a new probe in that module. It does not scan unrelated files, enumerate user records or delete a whole CloudKit zone.

Cancellation is a request, not a guarantee that an already-sent request stops. Moving the app to the background requests cancellation of active probes; system suspension may prevent cleanup from finishing. A save with an uncertain outcome can remain pending even if a later check cannot find the record.

Ownership and pending-cleanup tracking exist only in memory. Force-quitting, a crash or a restart can leave test data behind, and automatic recovery across launches is not implemented. Quitting or uninstalling the app does not guarantee immediate removal of cloud data or return of storage quota. Cloud storage reclamation is handled by Apple. If retry remains available, keep the original account and use that retry; after a restart, contact support about the remaining state rather than deleting unrelated data.
